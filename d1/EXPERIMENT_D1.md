# Исследование методов первичной маршрутизации обращений (D1)

Эксперимент D1 — сравнительное исследование лёгких алгоритмов классификации
текста пользовательского обращения по четырём взаимоисключающим интентам.
Цель — выбрать архитектуру первичного router'а медицинского AI-агента,
способную заменить вызов большой языковой модели на первом шаге диалога,
с обоснованной оценкой trade-off между качеством, безопасностью, латентностью
и стоимостью.

---

## 1. Контекст и прикладная ценность

### 1.1. Роль модуля в архитектуре агента

Первичная маршрутизация — самый частый шаг продукта: каждое входящее сообщение
проходит через router'а **до** того, как принимается решение о вызове LLM,
генерации сценарного ответа или передачи администратору. На этом шаге решается:

- какую сценарную ветку выполнять (запись на приём, ответ из FAQ, эскалация
  жалобы, отказ);
- следует ли вообще передавать сообщение в LLM (что стоит токенов и времени);
- нужно ли срочно поднять обращение как медицински-значимое (safety-режим).

Точность и предсказуемость этого шага определяет, во-первых, медицинскую
безопасность продукта (нельзя отвечать «прайс на консультацию» пациенту с
острой болью), во-вторых, экономику работы агента.

### 1.2. Экономия LLM-вызовов

Стандартная альтернатива закрытому классификатору — отправка каждого
обращения в LLM для intent-decoding. В рамках D1 этот подход сравнивается
со closed-set ML-классификатором, который:

- работает на CPU без сетевого вызова;
- даёт детерминированный ответ (одинаковый input → одинаковый output);
- не требует ни prompt-токенов, ни completion-токенов;
- имеет фиксированную задержку (sub-10 мс на самой тяжёлой модели);
- стоимость одного предсказания ниже LLM-вызова на 4–6 порядков (см. §9).

Прикладной выигрыш для агента: ~100% входящих обращений могут быть
классифицированы локально, и LLM вызывается только на сценарные ветки,
где она объективно нужна (генерация формулировок, перефразирование, анализ
истории диалога). Это переводит расходы на LLM из «за каждое сообщение»
в «за каждый полезный шаг сценария».

### 1.3. Проверяемая гипотеза

> Существует лёгкий closed-set классификатор интентов (rule-based / sparse /
> dense embedding), который на синтетическом стоматологическом корпусе
> достигает `macro_F1 ≥ 0.85` на основном тесте и `recall_urgent ≥ 0.90`
> на safety-выборке, при per-text latency ниже 10 мс на CPU.

Гипотеза проверяется без режима отказа: модель обязана вернуть одну из
четырёх меток. Это даёт честное сравнение архитектур, не зависящее от
порогов уверенности и пост-фильтров. Гипотеза в текущем эксперименте
**подтверждена**: четыре из пяти baselines удовлетворяют обоим условиям,
конкретный выбор кандидата определяется trade-offs (см. §11).

## 2. Постановка задачи и таксономия классов

Router классифицирует текст обращения в один из четырёх взаимоисключающих
доменов:

| Класс | Описание | Действие агента |
|---|---|---|
| `anamnesis` | Медицинская жалоба, симптом, боль, дискомфорт; пост-лечебные ощущения с медицинским содержанием. | Эскалация как медицинская тема, открытие сценария «сбор анамнеза». |
| `booking` | Запрос на запись на приём, перенос, отмена. | Сценарий записи. |
| `faq` | Информационный запрос: цены, услуги, документы, расписание, общая информация о врачах. | Ответ из базы знаний / FAQ-сценарий. |
| `unsupported` | Сообщение вне функциональных границ продукта: провокации, нерелевантное, политика, небезопасный контент. | Отказ или передача администратору. |

Закрытость таксономии существенна для замера качества: модель не имеет
права уйти в «не знаю». Это эквивалент режима «всегда выбрать одну из 4
кнопок» — ровно то, что делает router в production.

## 3. Сравниваемые baselines

В эксперимент включено по одному представителю каждого архитектурного
семейства, итого пять моделей. Все они зарегистрированы в
`BASELINE_CONFIGS` в [d1/baselines/trained_bundle.py](baselines/trained_bundle.py)
и обучаются через единый контракт (`fit`, `predict`, `predict_proba`).

| ID | Модель | Векторизатор | Голова | Параметры |
|---|---|---|---|---|
| **B0** | `B0_rules` | regex / keywords | rule-based | — |
| **B1.1** | `B1.1_tfidf_lr` | TF-IDF char_wb(2,5), max_features=50000 | Logistic Regression (saga, L2) | ~50 KB vectorizer + ~0.4 MB weights |
| **B1.3** | `B1.3_fasttext` | fastText supervised hashed n-grams | softmax linear | dim=100, epochs=25 |
| **B2.1** | `B2.1_bge-m3_svc` | sentence-transformers `BAAI/bge-m3` | LinearSVC + Platt | 568 M encoder params, dim=1024 |
| **B2.5** | `B2.5_e5-small_svc` | sentence-transformers `intfloat/multilingual-e5-small` | LinearSVC + Platt | 118 M encoder params, dim=384 |

**Логика выбора:** B0 — нижняя граница без обучения; B1.1/B1.3 — два разных
sparse-подхода (TF-IDF с явной матрицей против fastText с hashed embedding);
B2.1/B2.5 — две разные dense-модели разного размера (568 M vs 118 M) на
одной и той же голове (LinearSVC с Platt-калибровкой). Такой набор покрывает
все ключевые архитектурные семейства для классификации коротких текстов.

`LinearSVC` обучается через `CalibratedClassifierCV` с адаптивным числом
folds (см. `d1/baselines/b2_embedding.py::_adaptive_cv`), что даёт корректную
`predict_proba` и устраняет необходимость в дополнительных эвристиках
для безопасности.

## 4. Данные и стратегия оценки

### 4.1. Корпус

Корпус сгенерирован LLM (`x-ai/grok-4.1-fast`) по ролевой схеме с
последующим аудитом дубликатов и cross-split контаминации. LLM
использовалась **исключительно как генератор корпуса**, не как участник
inference. Размер train после full-cleanup deduplication — **2140**
сообщений.

### 4.2. Девять eval-выборок

Каждая выборка несёт отдельную исследовательскую задачу.

| Выборка | n | Распределение классов (anam / faq / book / unsupp) | Назначение |
|---|---|---|---|
| `train` | 2140 | 671 / 670 / 514 / 285 | Обучение всех baselines |
| `val` | 330 | 95 / 110 / 55 / 70 | Контроль обучения; не используется в финальной отчётности |
| `test` | 709 | 215 / 253 / 153 / 88 | **Основной in-distribution тест** |
| `hard_test` | 204 | 154 / 27 / 17 / 6 | Сложные формулировки: mixed_intent, упоминания врачей, post-treatment ambiguity |
| `safety_set` | 87 | 87 / 0 / 0 / 0 | **Safety-выборка**: только anamnesis с urgency ∈ {urgent, emergency, high} |
| `blind_test` | 38 | 12 / 12 / 8 / 6 | Held-out, не виданный в разработке |
| `entity_held_out` | 100 | 29 / 61 / 10 / 0 | OOD-проверка: сущности (врачи, специализации), отсутствующие в train |
| `extended_eval` | 101 | 0 / 101 / 0 / 0 | Edge-cases (singleton-class faq), smoke-тест |
| `switch_test` | 38 | — | Стресс смены интента; text-only режим |

**Принципы дизайна:**

- `test` отражает типичные обращения, на нём принимается основное решение
  о ранжировании моделей.
- `hard_test` намеренно содержит элементы, на которых интуитивно ожидается
  падение качества: короткие неоднозначные тексты («Лечение»), смесь намерений
  («У меня болит зуб, сколько стоит лечение?»), упоминания конкретных врачей,
  post-treatment ambiguity («Нормально ли что болит после пломбы?»).
- `safety_set` — синтетически сгенерированные ургентные кейсы; гарантирует,
  что метрика `recall_urgent` считается на достаточной выборке (n=87), а не
  на ≤17 ургентных кейсах внутри `test`.
- `entity_held_out` проверяет генерализацию по unseen named entities —
  один из главных факторов в production-устойчивости.
- `switch_test` — самый сложный сценарий: модель видит **только** текст
  второй реплики смены интента (без `active_domain` предыдущего
  диалога), что моделирует «слепую» работу text-only классификатора.

### 4.3. Контроль контаминации (anti-leakage)

Все split'ы прошли пять уровней проверки в `d1/scripts/split_dataset.py`
и `d1/scripts/leakage_audit.py`:

1. **Within-train deduplication** по нормализованному тексту
   (`_normalize_for_dedup`).
2. **Cross-split exact-text deduplication** — никаких совпадений между
   `train` и любой eval-выборкой.
3. **Cosine-deduplication** на эмбеддингах BGE-M3 с порогом
   `LEAKAGE_COSINE_THRESHOLD = 0.92`. Это убирает парафразы, не пойманные
   exact-match'ем (~29 строк в исходной версии корпуса).
4. **Seed-family check** — сообщения с одним `seed_id` не разбегаются по
   split'ам, чтобы не возникало контаминации через variation-шаблоны.
5. **Schema-validation** — все split'ы валидируются по `CSV_COLUMNS`.

Финальный audit отчёт фиксирует `cosine_leakage = 0` для всех eval-сетов
относительно train. Это критично — иначе сравнение моделей даст
артефактные высокие точности на пересекающихся кейсах.

### 4.4. Метрики

Метрики разделены на четыре функциональных блока. Каждая метрика имеет
ровно один источник истины (одна CSV/JSON).

| Блок | Метрики | Источник | Что измеряет |
|---|---|---|---|
| Качество классификации | `accuracy`, `macro_F1`, `balanced_accuracy`, per-class P/R/F1 (включая `anamnesis_recall`), `false_faq_for_anamnesis` | `baseline_results.csv` (`.json` для full precision) | Общее качество; per-class диагностика; самый опасный класс ошибок «жалоба → информационный ответ» |
| Безопасность | `recall_urgent`, `false_negative_urgent`, `misrouted_to` | `safety_results.csv` | Доля urgent-обращений, корректно поднятых в anamnesis; куда уходят пропущенные ургентные кейсы |
| Робастность к смене интента | `route_accuracy`, per-transition accuracy | `switch_results.csv` | Качество на коротких сменах темы в text-only режиме |
| Латентность | `encode_ms`, `predict_ms`, `total_ms` (median, p95) | `latency_breakdown.csv` (n=100, repeats=5) | Production-ориентированный замер времени per text на CPU |
| Калибровка | `ECE` (10 bins), `Brier OvR` (per-class + macro) | `calibration_metrics_*.json` | Соответствие предсказанной уверенности и реальной точности (только B1.1 / B2.1, у остальных predict_proba degenerate) |
| Стат. значимость | BCa 95% CI; paired bootstrap Δ + p-value + `significant` | `bootstrap_ci.csv`, `paired_tests.csv` (2000 ресэмплингов, rng_seed=42) | Различимость моделей с учётом размера выборки |
| Sample-efficiency | `mean ± std` по 5 seeds × {10/25/50/75/100%} train | `learning_curves_summary.csv` | Зависимость качества от объёма обучающих данных |
| Анализ ошибок | Multi-label rule-based теги (10 категорий) | `error_taxonomy_*.csv` | Категоризация ошибок: куда система «промахивается» и почему |

`recall_anamnesis` как отдельная safety-колонка из `baseline_results.csv`
удалена: на safety_set она арифметически совпадает с `recall_urgent`, а
на остальных eval-сетах дублирует `anamnesis_recall` из per-class блока.
Для сравнения моделей используется `macro_F1` (на in-distribution и
hard_test) + `recall_urgent` (на safety_set).

## 5. Результаты: качество классификации

### 5.1. Основной test (n=709, in-distribution)

**Таблица 5.1.** Closed-set метрики на `test`

| Baseline | macro_F1 | accuracy | balanced_acc | anamnesis_recall | false_faq_for_anam |
|---|---|---|---|---|---|
| **B2.1** BGE-M3 + SVC | **0.878** | **0.886** | **0.873** | 0.865 | 0.098 |
| B2.5 e5-small + SVC | 0.845 | 0.853 | 0.845 | 0.870 | 0.098 |
| B1.1 TF-IDF + LR | 0.840 | 0.863 | 0.822 | **0.884** | 0.102 |
| B1.3 fastText | 0.801 | 0.827 | 0.796 | 0.865 | 0.098 |
| B0 Rules | 0.421 | 0.391 | 0.482 | 0.298 | 0.005 |

**Интерпретация.** В in-distribution режиме архитектурное семейство
коррелирует с качеством: dense (B2.1, B2.5) ≥ sparse (B1.1, B1.3) ≫ rules.
B2.1 формально лидирует с macro_F1 = 0.878. Разрыв с B1.1 составляет
0.038 пункта, разрыв B1.1–B1.3 — 0.039 пункта (статистическая значимость
обсуждается в §8).

`anamnesis_recall` — лучший у sparse-модели B1.1 (0.884) при одновременно
несколько более высоком `false_faq_for_anamnesis`. Эти две метрики не
противоречат друг другу: B1.1 «более охотно» классифицирует пограничные
тексты как `anamnesis`, что одновременно повышает recall и долю
ложноположительных attribution'ов от faq-класса.

### 5.2. Сложные случаи (hard_test, n=204)

**Таблица 5.2.** Закрытая классификация на `hard_test`

| Baseline | macro_F1 | accuracy | balanced_acc | anamnesis_recall | false_faq_for_anam |
|---|---|---|---|---|---|
| **B1.1** TF-IDF + LR | **0.610** | 0.735 | 0.674 | **0.760** | 0.162 |
| B2.1 BGE-M3 + SVC | 0.598 | 0.711 | **0.724** | 0.701 | 0.208 |
| B1.3 fastText | 0.585 | 0.696 | 0.690 | 0.688 | 0.201 |
| B2.5 e5-small + SVC | 0.575 | 0.711 | 0.707 | 0.734 | 0.195 |
| B0 Rules | 0.465 | 0.657 | 0.619 | 0.740 | 0.033 |

**Ключевая инверсия.** На сложных формулировках B1.1 опережает все
dense-модели по macro_F1 и `anamnesis_recall`. Sparse-токенизация char-n-gram
оказывается более устойчивой к OOD-фразировкам, чем dense-эмбеддинги:
TF-IDF словарь не «связан» с конкретными формулировками train'а, и его
поведение деградирует плавнее.

Дополнительный сигнал: `false_faq_for_anamnesis` у dense-моделей растёт
до 0.20–0.21, у B1.1 — 0.16. То есть на сложных текстах dense-модели
**чаще** дают самый опасный класс ошибок (жалоба → FAQ-ответ).

Caveat: различия в группе {B1.1, B2.1, B1.3, B2.5} на `hard_test` находятся
в пределах бутстрап-шума при n=204 (paired bootstrap p > 0.23, см. §8).
Полученный тренд статистически не подтверждён, но направленно последователен.

### 5.3. Out-of-distribution (entity_held_out, n=100)

**Таблица 5.3.** Eval с unseen entities

| Baseline | macro_F1 | accuracy | anamnesis_recall | false_faq_for_anam |
|---|---|---|---|---|
| **B1.1** TF-IDF + LR | **0.637** | **0.880** | 0.793 | 0.138 |
| B2.1 BGE-M3 + SVC | 0.586 | 0.820 | 0.690 | 0.207 |
| B1.3 fastText | 0.563 | 0.770 | 0.655 | 0.241 |
| B2.5 e5-small + SVC | 0.546 | 0.710 | 0.517 | **0.414** ⚠ |
| B0 Rules | 0.241 | 0.160 | 0.103 | 0.034 |

**Серьёзный сигнал по B2.5.** На обращениях с unseen врачами/специализациями
**41.4%** жалоб у B2.5 классифицируются как FAQ. Модель «опирается» на
имена и термины, которых нет в train, и теряет robustness. Этот результат
disqualifying для безусловного выбора B2.5 как production-кандидата
без отдельной дообученной защиты от OOD entities.

B1.1 здесь — самая устойчивая модель: macro_F1 = 0.637 (на 5 пунктов выше
B2.1), `false_faq_for_anam` = 0.138 (втрое ниже B2.5).

## 6. Результаты: безопасность

### 6.1. Recall_urgent на safety_set (n=87)

**Таблица 6.1.** Safety-метрики

| Baseline | recall_urgent | FN_urgent | misrouted_to | false_faq_for_anam |
|---|---|---|---|---|
| **B2.1** | **0.931** | 6 | `{faq:3, booking:2, unsupp:1}` | **0.034** |
| B1.1 | 0.920 | 7 | `{faq:5, booking:1, unsupp:1}` | 0.058 |
| B2.5 | 0.920 | 7 | `{faq:3, booking:2, unsupp:2}` | **0.034** |
| B1.3 | 0.851 | 13 | `{booking:6, faq:5, unsupp:2}` | 0.058 |
| B0 | 0.747 | 22 | `{unsupp:22}` | 0.000 |

**Содержательная интерпретация.** Recall_urgent — главная метрика
безопасности продукта. Все ML-baselines преодолевают порог 0.85, четыре из
пяти — порог 0.90. Различие между B2.1 и B1.1 (Δ = 0.011) статистически
не значимо (paired bootstrap p = 0.74).

Однако само агрегатное число `recall_urgent` не отражает всей картины
безопасности. Содержательно важно, **куда уходят пропущенные кейсы**:

- B1.1: 5 из 7 FN ушли в `faq`. Это значит, что пациент с острой жалобой
  получит информационный ответ — самый токсичный класс ошибок.
- B2.1: только 3 из 6 FN ушли в `faq`, остальные — в `booking` (что хотя
  и неидеально, но всё же ведёт к взаимодействию с клиникой) и `unsupported`
  (хотя бы не вводит в заблуждение).
- B2.5: профиль 3/2/2 — наиболее равномерно распределённый misroute,
  но `false_faq_for_anamnesis = 0.414` на entity_held_out (§5.3) ставит
  под сомнение его pure safety на OOD.
- B1.3: при FN=13 это категорически отпадающий по безопасности кандидат.

### 6.2. Соотношение safety и качества

**Безопасность и качество корректировали друг друга по-разному:**

- B2.1 — Pareto-оптимальный по {recall_urgent, безопасный misroute профиль,
  in-distribution качество}.
- B1.1 — лучший на OOD по качеству, но безопасность чуть ниже B2.1 при
  худшем misroute-профиле на safety_set.
- B2.5 — заявленная безопасность на safety_set сопоставима с лидерами,
  но на entity_held_out ломается.

Выводы по безопасности должны делаться **на двух выборках одновременно**
(safety_set + entity_held_out), не только на одной.

### 9.1. Латентность (n=100, repeats=5, CPU)

**Таблица 9.1.** Per-text latency

| Baseline | total ms/text (median) | p95 (batch=100) | encode share |
|---|---|---|---|
| B1.3 fastText | **0.0032** | 0.338 | (внутр.) |
| B1.1 TF-IDF + LR | 0.0262 | 2.732 | 96% |

Для оценки экономии относительно LLM: даже самая медленная модель (B2.1 =

### 9.2. Калибровка (B1.1 и B2.1)

**Таблица 9.2.** ECE и Brier (macro OvR)

| Модель × eval | ECE | Brier (macro) |
|---|---|---|
| **B2.1 × test** | **0.071** | **0.043** |
| B1.1 × test | 0.211 | 0.069 |
| **B1.1 × hard_test** | **0.093** | 0.101 |
| B2.1 × hard_test | 0.114 | 0.108 |

**Диагональная инверсия лидера.** На in-distribution B2.1 калиброван в
три раза точнее B1.1, что подтверждает преимущество dense + Platt-калибровки
на «своих» данных. На hard_test картина меняется: B1.1 даёт более
«скромные» вероятности и оказывается точнее. B2.1 на сложных формулировках
становится over-confident — известная слабость dense-моделей вне их
training distribution.

Прикладной вывод: при использовании калибровки для confidence-gating
(переадресация на LLM при низкой уверенности), порог следует строить
по hard_test, а не по test — иначе он будет работать только на
типичных кейсах и пропускать сложные.

### 9.3. Sample-efficiency

**Таблица 9.3.** `macro_F1` на `test` × доля train (5 seeds)

| % train | B1.1 | B2.1 | Δ (B2.1 − B1.1) |
|---|---|---|---|
| 10% | 0.536 ± 0.063 | 0.717 ± 0.055 | +0.181 |
| 25% | 0.673 ± 0.040 | 0.798 ± 0.019 | +0.125 |
| 50% | 0.762 ± 0.041 | 0.832 ± 0.010 | +0.070 |
| 75% | 0.816 ± 0.017 | 0.864 ± 0.008 | +0.048 |
| 100% | 0.840 | 0.878 | +0.038 |

B2.1 на 25% train (n=535) достигает 0.798 — уровня, которого B1.1
достигает только на ≈ 50% train. Это двукратная sample-efficiency

которого sparse-модели нужно в 2 раза больше обучающего материала.

На hard_test картина другая: B2.1 насыщается уже на 75% train (0.609 →
0.598 при переходе на 100%), B1.1 продолжает расти до 100% (0.526 →
0.610). Это значит, что для B2.1 расширение train сверх ~75% не даёт
прироста, а для B1.1 — даёт.

явных правил поверх классификатора, либо отдельного safety-фильтра.

## 11. Обсуждение: сравнительная карта и архитектурные рекомендации

### 11.1. Архитектурные особенности и интерпретация результатов

В сравнении пяти baseline-моделей лидерство распределилось не по принципу
«одна модель лучше», а **по архитектурным свойствам относительно конкретного
среза данных**. B2.1 BGE-M3 + SVC лидирует на типовом потоке (`test`) и на
ургентных жалобах (`safety_set`); B1.1 TF-IDF + LR лидирует на сложных и
OOD-срезах (`hard_test`, `entity_held_out`). Это согласованный паттерн, а
не аномалия эксперимента, и он напрямую следует из различий в природе
признаков двух моделей.

**Таблица 11.1.** Архитектурные особенности B1.1 TF-IDF + LR и B2.1 BGE-M3 + SVC

| Свойство | B1.1 TF-IDF + LR | B2.1 BGE-M3 + SVC |
|---|---|---|
| Что видит | Подслова (char n-grams длиной 2–5) | Семантический эмбеддинг предложения (1024 dim) |
| Где обучалось распознавание | Только на стоматологическом train (`n = 2140`) | На общеинтернетовских мультиязычных текстах + contrastive objective |
| Природа признаков | Лексические и морфологические распределения слов домена | Семантический матчинг в высокоразмерном пространстве |
| Поведение на unseen entity | Плавная деградация через знакомые подслова | Резкая деградация: эмбеддинг сдвигается в неизвестный регион |
| Сильнее на | `hard_test`, `entity_held_out` (OOD-срезы) | `test`, `safety_set` (in-distribution срезы) |
| Production-ниша | Edge / mobile / CPU / детерминированный путь | Cloud / GPU / quality-режим |
| Footprint | ≈ 50 KB | 568 M params |
| Latency, мс/text | 0.026 | 7.46 |

**Интерпретация в одном выводе.** B2.1 BGE-M3 + SVC опирается на семантическое
сходство всего предложения и потому лучше работает там, где входящее сообщение
семантически близко к обучающему распределению: перефразированные жалобы,
типовые формулировки записи, привычные FAQ-вопросы. B1.1 TF-IDF + LR опирается
на распределение подслов и потому устойчивее на OOV-сущностях: незнакомые
фамилии врачей или специализации разлагаются в знакомые n-граммы и
классифицируются ближе к корректному классу, тогда как dense-энкодер выдаёт
для них эмбеддинг в неисследованной зоне, после чего линейный SVC принимает
решение по случайно-ближайшему классу.

Этот результат согласуется с устоявшимися наблюдениями в литературе: char-/
subword-level подходы исторически демонстрируют robustness к OOV и узким
доменам с малым train (Joulin et al., 2017; Bojanowski et al., 2017), а
плотные предложенческие энкодеры оптимизированы под retrieval-задачи
(contrastive matching), а не под small-domain closed-set classification
(Reimers, Gurevych, 2019; Chen et al., 2024). Лидерство sparse-модели на
OOD-срезах при сопоставимом качестве на in-distribution — ожидаемое
поведение архитектурной пары на этом классе задач, а не методическая ошибка.

### 11.2. Два направления для production

Из распределения лидерства следует, что для production-router'а корректно
рассматривать **два архитектурных пути, а не один**. Эти пути не
эквивалентны и характеризуются разными профилями рисков.

**Путь 1 — B1.1 TF-IDF + LR (лексический, локальный).**

- Ориентация на лексические и морфологические паттерны стоматологического
  домена.
- Целевая среда: edge / mobile / CPU. Latency 0.026 мс, footprint ≈ 50 KB,
  детерминированный ответ.
- Когда выбирать: словарь сущностей в продукте растёт со временем (новые
  врачи, услуги, специализации), приоритет — устойчивость к OOV, стабильность
  ответа, простота развёртывания и аудита.
- Главное ограничение: токсичный профиль misroute на safety_set (5 из 7 FN
  уходят в `faq`); требует ансамбля с rule-based safety-проверкой для
  ургентных кейсов.

**Путь 2 — B2.1 BGE-M3 + SVC (семантический, облачный).**

- Ориентация на семантический матчинг предложения.
- Целевая среда: cloud / GPU / MPS. Latency 7.46 мс, footprint 568 M params,
  лучшая sample-efficiency.
- Когда выбирать: in-distribution качество и safety-recall критичны, есть
  инфраструктура для dense-инференса, допустимо инвестировать в отдельный
  OOD-defence (NER-резолвер имён врачей, embedding-cache, фолбэк на B1.1
  при низкой уверенности).
- Главное ограничение: чувствительность к unseen entities
  (`false_faq_for_anamnesis = 0.207` на `entity_held_out`) и стоимость
  dense-инференса.

Выбор между этими путями определяется не результатами D1 в отдельности, а
внешними ограничениями продукта: целевой инфраструктурой, бюджетом на
инференс, скоростью обновления словаря сущностей и принятой стратегией
защиты от OOD. **Эксперимент D1 не указывает один «лучший» путь; он
показывает, что оба пути технически жизнеспособны и характеризуются разным
профилем сильных и слабых сторон.**

### 11.4. Рекомендации по сценариям применения

**B1.1 TF-IDF + LR.** Кандидат №1 для edge / mobile / low-latency. Лучшие
показатели на OOD (hard_test, entity_held_out), лучшая калибровка на
сложных кейсах, footprint в десять тысяч раз меньше dense-моделей, latency
0.026 мс. Основной риск — токсичный профиль misroute на safety_set
(5 из 7 FN уходят в faq); требует фолбэка или ансамбля с rule-based
проверкой для критичных сценариев.

**B2.1 BGE-M3 + SVC.** Кандидат №1 для cloud-production в high-quality
режиме. Лучшее агрегатное качество (test, blind_test, switch), лучшая
безопасность (recall_urgent + наименее токсичный misroute-профиль),
вдвое более sample-efficient, чем B1.1. Стоимость: 568 M параметров,
7.46 мс/text, чувствительность к unseen entities. Требует GPU/MPS или
embedding-cache для эффективной работы под нагрузкой.

**B2.5 e5-small + SVC.** **Не рекомендуется без дополнительной защиты от
OOD.** На entity_held_out `false_faq_for_anamnesis = 0.414` — каждая
вторая-третья жалоба от пациентов с unseen врачами/специализациями
переходит в FAQ. Это disqualifying для безусловного выбора в медицинском
сценарии. При наличии отдельного OOD-detector'а или гибрида с B1.1 как
fallback'ом — может быть рассмотрен.

**B1.3 fastText, B0 Rules.** Не рекомендуются как production-кандидаты:
B1.3 значимо хуже B2.1 на test и значимо хуже B1.1 на safety; B0 —
нижняя граница без обучения.

### 11.5. Применение в архитектуре AI-агента

Любой из трёх рекомендованных кандидатов закрывает первый шаг диалога
агента полностью без вызова LLM:

```
Входящее сообщение
   │
   ▼
[D1 Router]  ← локальный, sub-10 мс, без сетевого вызова
   │
   ├─ anamnesis  ─► сценарий сбора анамнеза + safety-эскалация
   ├─ booking    ─► сценарий записи
   ├─ faq        ─► retrieval-augmented ответ из БЗ
   └─ unsupported─► отказ или передача администратору
```

LLM подключается **только** на следующих шагах, где она объективно нужна:

- генерация уточняющего вопроса в сценарии анамнеза;
- перефразирование/нормализация запроса для retrieval;
- работа с историей диалога более 2–3 реплик.

### 11.6. Прикладной выигрыш и экономия LLM-вызовов

В предположении 1000 входящих сообщений в день и средней стоимости одного
LLM-вызова `≈ $0.0005 — $0.002` (зависит от модели и длины контекста):

- **Без router'а** — 1000 LLM-вызовов/день, **≈ $0.5 — $2.0/день** только
  на классификацию интента.
- **С D1 router'ом** — 0 LLM-вызовов на этапе intent-decoding;
  LLM остаётся только на сценарных шагах (предположительно 30–50% от
  потока), **≈ $0.15 — $1.0/день**.

Экономия токенов составляет 50–70% при сохранении сценарного качества.
По задержке: убираются 600–1500 мс LLM-round-trip с каждого первого
сообщения, что критично для UX чата.

## 12. Ограничения и направления развития

1. **Корпус синтетический.** Все обращения сгенерированы LLM по ролевой
   схеме. Несмотря на anti-contamination проверки, нельзя исключить
   систематические сдвиги распределения относительно реального потока
   пациентов. До production требуется пилот на обезличенных реальных
   обращениях с замером тех же метрик.

2. **`hard_test` насыщен на macro_F1 ≈ 0.60** — это «потолок» текущей
   архитектурной семьи. Дальнейший рост требует либо расширения train
   таргетными контр-примерами по доминирующим категориям ошибок (см.
   §10), либо гибридной архитектуры с эскалацией в LLM при
   `confidence < threshold`.

3. **Регрессия `recall_urgent` у B2.1 при росте train с 50% до 100%**
   (0.949 → 0.931) — наблюдается, требует проверки. Гипотеза: рост
   объёма не-anamnesis классов в train смещает prior. Проверка —
   повторный прогон с `class_weight="balanced"` на full train.

4. **B2.5 false_faq = 0.414 на entity_held_out** — требует анализа
   конкретных ошибок (см. `error_taxonomy_audit_sample.csv`). Возможные
   объяснения: переобучение на конкретных эмбеддингах имён врачей в
   train или особенность encoder'а multilingual-e5-small на русскоязычных
   терминах.

5. **switch_test text-only** — модель не получает диалоговый контекст.
   В production switch_accuracy будет выше за счёт state из истории
   реплик.

6. **Calibration не для всех моделей.** B0, B1.3, B2.5 не имеют
   корректной `predict_proba`. Для production-кандидата B2.5 потребуется
   калибровочный wrapper, если планируется confidence-gating.

7. **Размер blind_test (n=38) и extended_eval (n=101)** недостаточен для
   устойчивых CI; они служат корроборирующими, а не основными выборками.

## 13. Воспроизводимость

Все артефакты, обученные модели и метаданные прогона лежат в
[d1/results/](results/). Полный пересчёт пайплайна выполняется через

```bash
python -m d1.scripts.notebook_runner
```

или из ноутбука [D1_domain_router_v6.ipynb](D1_domain_router_v6.ipynb).
Cache моделей в `d1/results/models/` инвалидируется автоматически по
5-компонентному `CacheKey` (params / dataset / code / env / schema);
`bundle_metadata.json` фиксирует хеши, размер train и время обучения
каждого baseline'а.

Запуск тестового набора — `pytest d1/tests/ -q`.
